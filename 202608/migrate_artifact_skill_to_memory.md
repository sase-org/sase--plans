# Plan

## Scope and design

Treat this as the artifact analogue of the completed `sase_beads` migration: ship one
project-only packaged long-memory template, make memory initialization own its generated
copy and instruction references, then retire the redundant bundled skill source. Keep
the change atomic so no released state advertises both competing instruction sources or
neither source.

The new note must describe the domain model before commands:

- An artifact is any durable record with a canonical `<kind>:<argument>` identity,
  including sidecar documents, beads, agents, Patches, stitches, and indexed files. The
  leading `@` belongs to prompt citations, not stored identities or ordinary CLI
  arguments.
- Artifact references provide identity, resolution, prompt expansion, publication, and
  consumption tracking. `sase artifact list` is specifically the indexed-file inventory
  and must not be presented as a list of every artifact.
- Indexed files are either explicit snapshots created by an agent or automatic captures;
  automatic captures may retain bytes or a verified VCS locator. Canonical archived
  prompts remain in the agents sidecar and are inspected with `sase agent prompts`, not
  through the file-index mental model.
- Typed links connect durable artifacts and project into artifact Markdown pages. Manual
  `link add` accepts `related`, `supersedes`, `implements`, and `derives-from`; `cites`
  and `read` are written by prompt expansion and audited reads. Scheduling relationships
  remain bead dependencies.

Keep the body intentionally compact and decision-oriented. Prefer
`sase artifact <subcommand> -h` for exhaustive flags and retain only the workflows and
safety rules an agent must remember:

1. Consume context with `sase artifact read <ref> "<reason>"`; use `show` for metadata,
   `path` for composition, and `open` for a viewer.
2. Register a produced deliverable with `sase artifact create -p <path> -l "<label>"`,
   optionally attaching the minted `file:` ref to a bead. Explain that this is an
   immutable, permanent explicit snapshot and that `--move` is appropriate only for a
   disposable source.
3. Discover indexed files with `list`; do not imply that the command enumerates plans,
   beads, Patches, stitches, or agents.
4. Add deliberate manual links with a one-line reason and bare canonical refs; mention
   the generated Tier 1 relation registry rather than duplicating all of its data.
5. Preserve the lifecycle guardrails: explicit and persistently referenced/consumed
   files are protected; automatic captures can be reclaimed or pruned; `prune` and
   `reclaim` are previews until `--apply`; removal goes to restorable trash; purge is
   irreversible. Agents must not apply lifecycle mutations or purge without explicit
   user authorization. Avoid low-value implementation detail and unstable exhaustive
   flag lists.

The frontmatter should be `type: long`, `parent: AGENTS.md`, with a concise description
that tells agents to read it before creating, consuming, resolving, linking, or managing
artifact retention. Target a materially smaller context footprint than the retired skill
while preserving the rules above.

## Generated memory integration

Add `memory-sase-artifacts.template.md` beside the other packaged memory templates and
register `sase/memory/sase_artifacts.md` as a project-only generated long note in
`src/sase/main/init_memory/root_rendering_notes.py`. Extend the authoritative generated
path inventory and project commit staging in
`src/sase/main/init_memory/project_deploy.py`. Reuse the existing generic long-note
rendering path so frontmatter normalization, Tier 2 description injection, README
inventory, home-root retirement, mutation protection, and idempotent drift planning all
behave exactly like `sase_beads.md`; do not add a parallel artifact-specific renderer.

Update the packaged memory README prose and the memory/init documentation to describe
all generated project-only long notes accurately. Update tests that assert exact
generated-path sets, Tier 2 entries/order, project-versus-home behavior, generated-note
immutability, project staging, Markdown formatting, and wheel contents. Add focused
coverage proving that a managed-project memory plan and the bare `sase init --yes`
memory path create `sase_artifacts.md`, include it in generated `AGENTS.md` and provider
copies, list it in `sase/memory/README.md`, and converge to no drift on the next plan.
Keep home and chezmoi-home roots free of the packaged project-only note, while
preserving the existing rule that a human-authored home note with the same stem is
allowed.

Add a small contract test for the commands shown in the new template. Parse the examples
through the real CLI parser and assert the conceptual distinctions most likely to
regress: `read` requires a reason, `create` produces a file artifact, and only
CLI-writable link relations appear in a manual-add example.

## Retire the xprompt skill

Delete `src/sase/xprompts/skills/sase_artifact_file.md`. Remove its bundled-skills row
from `docs/xprompt.md`, its source-integrity phrase fixture, its packaged-skill
rendering expectations, and the wheel assertion that ships the old source. Replace that
wheel assertion with one for the new memory template. Leave historical transcript
fixtures and immutable archive data untouched.

Do not add a compatibility skill shim or a bare `#sase_artifacts` alias. The supported
replacement is the generated Tier 2 entry, read through `/sase_memory_read` as
`sase_artifacts.md` (and explicitly expandable as `#memory/sase_artifacts` under the
existing memory namespace). Do not deploy or hand-edit provider `SKILL.md` files from
the working tree; source retirement follows the same package/deployment boundary as the
prior beads migration.

## Regeneration and verification

After source and test updates, run `just install`, then focused tests for memory
rendering/planning/application, bare-init onboarding, generated-note mutation guards,
skill discovery/rendering, command examples, and wheel packaging. Run
`sase memory init --no-commit` as the user-authorized mandatory regeneration step so the
canonical `sase/memory/sase_artifacts.md`, `AGENTS.md`, provider instruction copies, and
`sase/memory/README.md` are refreshed from the packaged template. Inspect the generated
diff for byte-for-byte provider-copy consistency, the intended Tier 2 description, and
the note's token count; tighten the template if any paragraph merely restates CLI help
or Tier 1 artifact-relation content.

Re-run the focused tests after regeneration, then require both
`sase memory init --check` and `sase init --check` to report no memory drift. Finish
with `just check`; if its scoped selector escalates or reports unusual selection, run
`just check-full` through `/sase_monitor` as required. Preserve unrelated working-tree
changes throughout.

## Acceptance criteria

- A fresh managed-project `sase init` generates `sase/memory/sase_artifacts.md`, exposes
  its description in Tier 2 of every generated provider instruction document, and lists
  it in the memory README; a second initialization is a no-op.
- The generated note is project-only, recognized as SASE-owned/read-only by memory
  mutation surfaces, auditable through `sase memory read sase_artifacts.md`, and
  available through `#memory/sase_artifacts` by the existing generic loader.
- The note accurately distinguishes the artifact universe, references, indexed files,
  prompt archives, and typed links; it corrects manual relation ownership and retains
  the explicit-artifact and lifecycle safety contracts without duplicating CLI help.
- The bundled `sase_artifact_file` source and current documentation/tests that advertise
  it are gone, while historical fixtures remain unchanged.
- Regenerated repository instruction files are consistent, all targeted tests pass,
  `sase memory init --check` is clean, and `just check` passes.
