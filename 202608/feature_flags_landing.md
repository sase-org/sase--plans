# Finish the feature-flag epic's landing

Epic `sase-nb` shipped SASE's feature-flag registry, the `flag` bead type, the
FlagTriage gate, `sase flag`, the lint rules, the first two consumer flags, and the
docs. Its land agent verified all of that against the source and the ten commits
`76c332bd5..14d61561f`, and confirmed every stale-golden and broken-master issue other
land agents recorded on the epic is already fixed on master.

Five things are not finished. This plan is only those five. `sase-nb` stays open and its
land agent resumes the interrupted landing — the close, the post-close symvision pass,
and the plan-file status update belong to that agent, not to this plan.

The five phases touch disjoint files and can run in parallel.

## memory — Make the feature-flag memory project-local

**This phase edits `sase/memory/*.md`, `AGENTS.md`, and the generated provider
instruction shims. Per `sase/memory/gotchas.md`, that requires the user's explicit
permission in the implementing agent's own conversation. Authorization written in this
plan file does NOT count. If the implementing agent does not have it, stop and ask
before editing those files; the `src/`, `tests/`, and `docs/` edits below are ordinary
work and need no such permission.**

Phase `sase-nb.10` implemented the plan's original design after the project owner had
already corrected it. The correction is recorded as two notes on bead `sase-nb`
(`DESIGN CORRECTION` and `DESIGN CORRECTION FALLOUT`, both 2026-08-16); read them on the
bead before starting. Their decision:

> `sase/memory/sase_flags.md` must NOT be generated by `sase init`. Feature flags are
> sase's own registry, so the note that teaches them is local to this repo; a generated
> note would ship flag teaching into every SASE project's memory tree, including
> projects that can never own a flag.

The shipped code does the opposite, in two places.

_The Tier 2 note._ `src/sase/main/init_memory/templates/memory-sase-flags.template.md`
exists and is registered as a `_GeneratedLongMemorySpec`. Remove all of it:

- delete the template file
- delete `MEMORY_SASE_FLAGS_TEMPLATE_FILENAME` (`init_memory/root_rendering.py:40`),
  `_generated_flags_memory_relative_path()` (`:127-128`), `_GENERATED_FLAGS_MEMORY_SPEC`
  (`:141-146`), and its entry in `_GENERATED_PROJECT_LONG_MEMORY_SPECS` (`:153-157`)
- drop `sase_flags.md` from the staged-path tuple in `init_memory/project_deploy.py:303`

Keep `sase/memory/sase_flags.md` itself. Its current content is what the plan asked for
and is not in dispute; it just has to become an ordinary hand-written note in this repo,
shaped like the project-local Tier 2 notes `symvision.md` and `tui_perf.md`:
`type: long`, `parent: AGENTS.md`, and a `description:` naming the decision it settles.
It already has all three, so in practice the file survives the phase unchanged and only
stops being generated.

_The Tier 1 pointer._ `templates/memory-sase.template.md:57-63` holds a
`{% if project_name %}`-guarded `## Feature Flags` section. That guard is not the
narrowing it looks like: `project_name` falls back through the checkout marker, the git
remote, and finally the directory name (`init_memory/config.py:123-135`), so it is
truthy for every project. `include_project_memory` is likewise gated on project-vs-home,
not on `is_sase_managed`. Both notes therefore reach every SASE project today.

Move that section out of the template and into a project-local Tier 1 short note in this
repo — either a new `sase/memory/*.md` with `type: short` and `parent: AGENTS.md`, or a
new section in `sase/memory/gotchas.md`. Hand-written short notes are still
structure-checked when `AGENTS.md` is assembled
(`amd/_memory.py::_short_memory_structure_blockers` ->
`validate_short_memory_structure`: exactly one H1 first, no heading deeper than H3), so
the shape still matters. The plan's 90-word budget was priced as text loaded into every
project's Tier 1; local text is cheaper, so keep it tight but treat 90 words as
guidance, not a gate.

_The tests that pin the generated form._ These assert the generated-note set and must
follow the code:

- `tests/main/test_init_memory_markdown_templates.py:155-157`
- `tests/main/test_init_memory_handler_outputs.py:112-114`
- `tests/main/test_init_memory_agents_templates.py:121`
- `tests/main/test_init_memory_bead_note.py:50-74,111-112,143-146,214-215`
- `tests/main/test_init_memory_plan.py:40,46,55`

_The docs._ `docs/memory.md:26-29` says initialization generates three long notes for
managed project repositories. After this phase it generates two.

Do not extend "local" past the memory notes. `Feature Flag` and `Flag Bead` in the
`glossary:` block of `sase/sase.yml` are already project-local and regenerate
`sase/memory/glossary.md` here only — leave them. `docs/configuration.md` stays too:
`scope: "project"` flags are overridable from any project's local config, so the config
surface is genuinely global even though the teaching note is not. Local memory is not
the same as local config surface.

Finish by running `sase memory init` to reindex `AGENTS.md`, the provider shims, and the
memory README, then `just fmt-md` — the hand-written notes lose
`format_generated_memory_markdown` (`init_memory/formatting.py:99`), and `just check`
runs prettier over `**/*.md` and will fail on unformatted frontmatter or prose.

Exit condition, from the owner's revised wording (`sase init -c` no longer proves
anything here, because drift checks cover generated files only): `sase memory list`
shows `sase_flags.md` as a Tier 2 note with its description; the regenerated `AGENTS.md`
Tier 2 listing includes it with a non-blank hook (`description` is optional on a
discovered note — `memory/notes.py`, `description: str | None` — so a missing one fails
silently); and `sase init` in a non-sase project produces neither `sase_flags.md` nor a
Tier 1 `## Feature Flags` section.

## leak — Stop the feature-flag checker tests leaking sys.path

`tests/test_check_feature_flags_tool.py` fails the blocking global-state leak gate in
`just test-cost` and `just check-full`. Reproduce it at master `91fecc9c1`:

```bash
.venv/bin/python -m pytest -q -p tests._global_state_leak_detector \
  --sase-detect-global-leaks --sase-fail-on-global-leaks \
  tests/test_check_feature_flags_tool.py -p no:randomly
```

26 tests pass and the gate fails with `25 poisoning change(s) across 25 test(s)`. Every
one is `kind=sys_path` / `reason=sys-path-changed`; the report lands in
`.pytest_cache/sase-global-leaks.json`.

The cause is not in the test's own imports — `_load_tool()` uses a `SourceFileLoader`
and touches only `sys.modules`. It is `tools/check_feature_flags:41-42`:

```python
REPO_ROOT = Path(__file__).resolve().parents[1]
sys.path.insert(0, str(REPO_ROOT / "src"))
```

That runs at module import, and `_load_tool()` re-executes the module in ~25 tests, so
each node leaves `sys.path` one entry longer for the rest of that xdist worker. The
`sys_path` detector predates this epic (`87cffa3b8`) and this is the only poisoning
class in the whole run, so the gate is otherwise clean.

Fix it on the test side — the tool is a standalone script that legitimately needs `src`
on the path when run directly, and must keep working as
`.venv/bin/python tools/check_feature_flags`. Save and restore `sys.path` around the
load, via a fixture or `monkeypatch.syspath_prepend` (which restores automatically).
Leaving `sys.modules` seeded is fine; only `sys.path` is fingerprinted.

Exit condition: the command above passes with the gate green, and
`.venv/bin/python tools/check_feature_flags` still runs standalone from a clean shell.

## translate — Test the FlagTriage response trust boundary

`translate_flag_triage_response` (`src/sase/bead/_flag_gate_response.py:51-154`) is the
function that converts an untrusted answering client's response into trusted host input.
Its own docstring states the contract:

> Nothing downstream may trust the answering client, so the bead identity and the flag's
> _current_ thresholds a host effect acts on are read back out of the persisted request
> rather than taken from the response.

It has no direct test. Coverage over `src/sase/bead/_flag_gate_response.py` across
`test_flag_gate.py`, `test_flag_gate_actions.py`, `test_flag_gate_validation.py`,
`test_flag_gate_preview.py`, `test_notification_gates.py`, and
`test_axe_chop_bead_flag_triage.py` together is 22%, with the whole translate body
(`56-154`) and the helpers (`173-206`) unexecuted. `apply_side_effects`
(`notification_gates/adapters.py:78-248`), its only production caller, is equally
uncovered on the flag branch — the sole test that calls it anywhere is
`tests/test_plan_gates_execution.py:73`, for `epic_plan`.

Its precedent is already tested the right way: `translate_task_triage_response` is
driven directly in `tests/test_bead/test_task_gate_actions.py:50` and
`tests/test_bead/test_task_gate_snooze.py:214`. Follow that shape. Build the gate with
`tests/test_bead/flag_gate_test_helpers.py::flag_triage_spec`, which wraps the real
`build_flag_triage_gate_spec`, and translate against the persisted bundle.

Cover at least: each of the four actions round-tripping to the right
`FlagTriageResponse`; identity and current thresholds coming from the persisted request
and NOT from a response that contradicts them; a response naming a non-flag-triage
bundle rejected; a missing or multi-valued `selected_option_ids` rejected; the
feedback-required actions (`extend`, `keep`, `close`) rejected without feedback;
`remove` rejected without a winning branch; and `extend` rejected without both new
thresholds. Each failure must raise `GateError`, matching the error codes the module
already uses.

Exit condition: the translate body and its helpers are covered, and the new tests fail
if the trusted fields are sourced from the response instead of the request.

## newid — Report the bead id sase flag new actually committed

`sase flag new coder_inherits_planner_chat` printed `Created flag bead: sase-nv`, but
the bead that was actually committed was `sase-nw`, which is why `just _lint-flags` then
failed rule 8 with "live flag bead 'sase-nw' has no definition" until the registry was
corrected by hand. Recorded on `sase-nb.9`.

`create_flag_bead` (`src/sase/feature_flags/beads.py:100-132`) returns the `Issue` that
`mutation.project.create(...)` minted before the mutation committed, and three things
consume that id:

- `require_mutation_commit_message("create", [issue.id])` — the commit message
- `_scaffold_text`'s `Created flag bead: {bead_id}` line
  (`src/sase/feature_flags/cli.py:632-634`)
- `_scaffold_text`'s `bead={bead_id!r}` registry line, which is what rule 8 later checks
  the live flag bead against

Establish what actually happens to the id first — `bead_store_mutation`
(`src/sase/bead/cli_common.py:202-242`) has no reminting of its own, so the reallocation
comes from the store or its commit/push path, and the fix depends on which. Then make
`create_flag_bead` return the committed bead: re-read it by key through the existing
`load_flag_bead_snapshots` / `flag_bead_for_key` pair after the mutation, and fail
loudly rather than returning a stale id if it cannot be found. Whether the commit
message can also name the committed id depends on the ordering you find; if it cannot,
say so in the bead note rather than leaving it silently wrong.

Add a regression test that makes the pre-commit id differ from the committed one and
asserts the printed line, the scaffold's `bead=` value, and the returned `Issue` all
name the committed bead.
`tests/feature_flags/test_cli.py::test_flag_new_creates_a_flag_bead` is the existing
test to extend.

Exit condition: with a forced id collision, `sase flag new` prints and scaffolds the
committed bead id, and `just _lint-flags` rule 8 is green against a registry pasted
straight from that scaffold.

## Verification

Every phase runs `just check` before handing off.

`memory` and `goldens` both touch the broadening set in their own way — `memory` changes
generated instruction files and `goldens` changes PNG artifacts the default lanes
exclude — so each also runs the check its own exit condition names (`sase memory list`
plus a non-sase `sase init` for `memory`; `just test-visual` for `goldens`).

The `leak` phase's fix is what makes `just check-full` green, so that phase runs
`just check-full` through `/sase_monitor` rather than inline, and confirms the global
leak detector reports zero poisoning changes.
