# Remove the hand-written CHANGELOG `Unreleased` section and guard against its return

## Problem

`CHANGELOG.md` in this repo is generated by release-please. The tooling is configured in `release-please-config.json`
(`"release-type": "python"`), `.release-please-manifest.json` (`{".": "0.13.3"}`), and the `release` job in
`.github/workflows/publish.yml`, which runs `googleapis/release-please-action@v5` on every push to `master`. Every
`## [x.y.z](https://github.com/sase-org/sase/compare/...) (date)` section below the top of the file was written by that
action from conventional commit subjects.

Despite that, the file currently opens with a hand-written section:

```
# Changelog

## Unreleased

### ⚠ BREAKING CHANGES
...
### Features
...
### Bug Fixes
...

## [0.13.3](https://github.com/sase-org/sase/compare/v0.13.2...v0.13.3) (2026-07-29)
```

This section is wrong, and it is wrong in a way that will not self-correct:

1. **It is not release-please's format.** It uses `-` bullets and prose-wrapped text; generated entries use `*` bullets
   with a trailing commit link.
2. **It is permanent.** release-please inserts each new version section immediately above the previous highest version
   heading, i.e. _below_ `## Unreleased`. It never parses, consumes, or removes the block. It has already survived five
   releases (v0.11.0 through v0.13.3).
3. **Its content is already released.** Every entry describes a commit that shipped in v0.11.0–v0.13.3, so readers see
   shipped work advertised as unreleased.

The block was introduced by commit `7776f7a85` (`feat(ace): add inline xprompt property editing`, 2026-07-10) and was
appended to by later feature commits (`605b7baa1`, `0138849d9`, `58765147a`, `14bf5f15c`, `6c4b65f7b`, `98a3d9c4e`,
`3694f5a48`, `a49e63e35`). Nothing in the repo asks contributors to hand-edit the changelog — `CONTRIBUTING.md` says
nothing about it, and `src/sase/xprompts/skills/sase_git_commit.md` explicitly explains that commit tags drive
release-please changelog generation. This was agent improvisation, and it needs a mechanical guard rather than another
prose reminder.

three get backfilled into the version section where their commits shipped (all three are v0.12.0); everything else is
deleted.

## Goals

1. `CHANGELOG.md` contains only release-please-generated sections.
2. No user-visible information is lost: the three genuinely-missing entries land in the correct released section, in
   release-please's own format.
3. A hand-written section cannot silently reappear — `just lint` / `just check` / CI fail on it.
4. Contributors and agents have a one-line written statement that the file is generated.

## Non-goals

- Do **not** rewrite, reflow, reformat, or re-sort any existing generated section. `CHANGELOG.md` is in
  `.prettierignore`, so its long lines are intentional; leave them alone.
- Do **not** change release-please configuration, the `publish.yml` workflow, or the manifest version.
- Do **not** cut a release or bump a version as part of this work.
- Do **not** try to make release-please retroactively regenerate the 0.12.0 section.
- Do **not** backfill the `test(ace): add Chats visual snapshots` bullet. release-please's Python preset intentionally
  omits `test:` commits; adding it by hand would reintroduce exactly the drift this plan removes.

## Implementation

### Step 1 — Delete the `Unreleased` block

In `CHANGELOG.md`, delete from the `## Unreleased` line through the blank line preceding
`## [0.13.3](https://github.com/sase-org/sase/compare/v0.13.2...v0.13.3) (2026-07-29)` (currently lines 3–38). The file
must then begin exactly:

```
# Changelog

## [0.13.3](https://github.com/sase-org/sase/compare/v0.13.2...v0.13.3) (2026-07-29)
```

### Step 2 — Backfill the three missing entries into the v0.12.0 section

The v0.12.0 section starts at `## [0.12.0](...)` (currently `CHANGELOG.md:221`) and ends where `## [0.11.1](...)`
begins. Within each generated subsection, entries are sorted; insert each new bullet at its correct sorted position
rather than appending. Use the exact generated bullet shape — `* ` prefix, `**scope:** ` where the commit had a scope,
the commit subject verbatim, and a trailing `([<7-char sha>](https://github.com/sase-org/sase/commit/<40-char sha>))`
link. Keep each bullet on a single line (no prose wrapping) to match its neighbours.

Add to the v0.12.0 `### ⚠ BREAKING CHANGES` list (these are prose migration notes, no commit link, matching the existing
bullets there):

- The tribe rename, phrased from `0138849d9`'s `BREAKING CHANGE:` footer — current agent APIs, wires, metadata, queries,
  and display terminology use tribe instead of tag; standalone assignments live in `~/.sase/agent_tribes.json` under
  `tribe`; the Agents query uses `tribe:` instead of `tag:`; legacy persisted tag data remains readable.
- The axe description grammar constraints from the deleted block — line 1 must be a non-blank summary of at most 100
  characters, a multi-line description must leave line 2 blank, and the whole description must be at most 2000
  characters; violations fail config loading with `description_summary_blank`, `description_summary_too_long`,
  `description_body_separator_required`, or `description_too_long`.

Add to the v0.12.0 `### Features` list:

```
* **agents:** complete tribe terminology cutover (sase-7j.4) ([0138849](https://github.com/sase-org/sase/commit/0138849d919e0136b6eedadbcfb28e603f2b58bb))
```

Add to the v0.12.0 `### Bug Fixes` list:

```
* **ace:** remove clan and family identity icons ([605b7ba](https://github.com/sase-org/sase/commit/605b7baa1d4a9a95b4188f32fb69a05d23031eab))
```

Verify each subsection heading exists in the v0.12.0 section before inserting; do not create new subsections.

### Step 3 — Add the `tools/validate_changelog` guard

Create an executable `tools/validate_changelog` (mode `755`, `#!/usr/bin/env python3`,
`from __future__ import annotations`), following the structure of the existing `tools/validate_dependency_group` and
`tools/validate_test_environment` scripts: module docstring, private helpers, a public entry function, `main()`
returning an exit code, and a `if __name__ == "__main__": sys.exit(main())` tail. Standard library only.

Behavior:

- Read `CHANGELOG.md` from the repo root (resolve via `Path(__file__).resolve().parents[1]`, as the sibling validators
  do) and scan it line by line.
- The only accepted `#` heading is the literal first-line `# Changelog`.
- The only accepted `## ` headings are release-please version headings. Match with a regex equivalent to
  `^## \[\d+\.\d+\.\d+\]\(https://github\.com/sase-org/sase/compare/v\d+\.\d+\.\d+\.\.\.v\d+\.\d+\.\d+\) \(\d{4}-\d{2}-\d{2}\)$`,
  and also accept the two pre-`compare` forms already present near the bottom of the file — check the oldest sections
  (0.1.x / 0.2.0) before finalizing the pattern and widen it only as far as the real historical headings require.
- `### ` headings are unconstrained (release-please emits `### Features`, `### Bug Fixes`, `### ⚠ BREAKING CHANGES`,
  `### Performance Improvements`, `### Documentation`, `### Miscellaneous Chores`, and more; do not hardcode a list).
- Ignore headings inside fenced code blocks (track ``` fences) so a future generated entry quoting Markdown cannot trip
  the check.
- On violation, print to stderr in the `[validate_changelog] ...` prefix style used by the sibling tools, naming the
  offending line number and text, and explaining the fix: CHANGELOG.md is generated by release-please from conventional
  commit messages; describe the change in the commit subject/body instead of editing this file. Exit 1. Exit 0 when
  clean.

### Step 4 — Wire the guard into lint and CI

In the `Justfile`:

- Add a private recipe next to the other `_lint-*` recipes:

  ```
  # Check that CHANGELOG.md contains only release-please sections (private, extracted for per-stage wrapping)
  _lint-changelog: _setup
      {{ venv_bin }}/python tools/validate_changelog
  ```

- Call it from the `lint` recipe with a matching `@printf "\n---------- ... ----------\n"` banner line, following the
  established pattern.
- Add a `@tools/run_silent "lint (changelog)"   just _lint-changelog` line to the `check` recipe, aligned with its
  neighbours.

CI needs no edit: `.github/workflows/ci.yml`'s `lint` job runs `just lint`, so the new stage is picked up automatically.
Confirm this rather than adding a separate CI step.

### Step 5 — Add a test for the guard

Add `tests/test_validate_changelog_tool.py`, following the loader pattern in
`tests/test_validate_dependency_group_tool.py` (`SourceFileLoader` + `importlib.util.spec_from_file_location`,
`ROOT = Path(__file__).resolve().parents[1]`). Cover:

- the repo's real `CHANGELOG.md` passes (this is the regression lock for Steps 1–2);
- a `## Unreleased` heading in a temporary file fails;
- some other stray `## Some Heading` fails;
- a malformed version heading (e.g. missing date) fails;
- a well-formed generated file with several version sections and `###` subsections passes;
- a `## Unreleased` line inside a fenced code block does **not** fail.

### Step 6 — Document that the file is generated

Add a short `## Changelog` section to `CONTRIBUTING.md` (between `## Adding Dependencies` and
`## Running Specific Tests`), stating that `CHANGELOG.md` is generated by release-please from conventional commit
messages, that it must never be hand-edited (there is no `Unreleased` section — `just lint` enforces this), and that the
way to add a changelog entry is to write a proper `feat:` / `fix:` commit subject with a `BREAKING CHANGE:` footer where
applicable. Keep it to a few lines and match the surrounding style; `CONTRIBUTING.md` is prettier-formatted at
`--prose-wrap=always --print-width=120`.

### Step 7 — Ask before touching SASE memory

A `gotchas` entry in `sase/memory/gotchas.md` ("CHANGELOG.md is generated; never hand-edit it") would be the durable fix
for agent behavior, but memory files must not be edited without the user's explicit permission in the conversation — and
permission stated in _this plan file_ does not count. Do not edit `sase/memory/*.md`, `AGENTS.md`, or the generated
provider shims as part of this work. Instead, when reporting completion, ask the user whether they want that memory
entry added as a follow-up.

## Verification

1. `just install` first (ephemeral workspace), then `just check`. This exercises `fmt-md-check` (which skips the
   prettier-ignored `CHANGELOG.md` but does check `CONTRIBUTING.md`), the new `lint (changelog)` stage, and the new
   test.
2. `./.venv/bin/python tools/validate_changelog` exits 0 against the cleaned file, and exits 1 with a clear message when
   `## Unreleased` is temporarily re-added.
3. `head -5 CHANGELOG.md` shows `# Changelog`, a blank line, then the `## [0.13.3]` heading.
4. `grep -c '^## Unreleased' CHANGELOG.md` returns 0.
5. The three backfilled bullets render correctly: their commit links resolve to `605b7baa1` and `0138849d9`, and they
   sit inside the v0.12.0 section, not v0.13.x.
6. `git diff` touches only `CHANGELOG.md`, `CONTRIBUTING.md`, `Justfile`, `tools/validate_changelog`, and
   `tests/test_validate_changelog_tool.py`.

## Commit guidance

The changelog cleanup itself is not a user-facing behavior change; the guard is repo tooling. Use a `chore:`-tagged
commit (for example `chore(changelog): drop the hand-written Unreleased section`) so release-please does not create a
version bump for this work, and mention in the body that release-please owns the file. Follow the repo's commit skill
rather than invoking `git commit` directly, and only commit if the user asks.
